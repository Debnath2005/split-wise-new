# ADR-0003: SQLite with Drizzle ORM and better-sqlite3

- **Status:** Accepted
- **Date:** 2026-10-01
- **Spec refs:** SPEC §2 (D4), §3, §5, §12

## Context
The MVP targets about 1k users on one server. We want a typed schema, migrations and real transactions, with no separate DB server to run.

## Decision
- Use SQLite in WAL mode with `foreign_keys=ON` and `busy_timeout=5000`.
- Access it through **better-sqlite3** (synchronous driver) and **Drizzle ORM**. Migrations are generated by **drizzle-kit** and committed.
- Every multi-row write runs inside a better-sqlite3 transaction.
- Back up the DB file daily with `sqlite3 .backup`.

## Consequences
- Running and deploying is simple: one file and one persistent volume. Tests use in-memory SQLite.
- Only one process can write, so we scale vertically. Moving to Postgres later means swapping the Drizzle dialect, and any raw SQL would need to be ported.
- The synchronous driver keeps transactions simple, but long queries block the event loop. Keep queries indexed (SPEC §5 indexes).

## Alternatives considered
- **Prisma**: heavier, with a separate engine and limits on SQLite.
- **Raw SQL**: no typed queries.
- **Postgres**: more to run than the MVP needs.
